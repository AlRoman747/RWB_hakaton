# Контракты данных и компонентов

## 1. CSV → загрузчик

Каталог `data/` должен содержать ровно следующие обязательные источники (дополнительные файлы игнорируются):

| CSV | Таблица |
|---|---|
| `olist_customers_dataset.csv` | `raw.customers` |
| `olist_geolocation_dataset.csv` | `raw.geolocation` |
| `olist_order_items_dataset.csv` | `raw.order_items` |
| `olist_order_payments_dataset.csv` | `raw.order_payments` |
| `olist_order_reviews_dataset.csv` | `raw.order_reviews` |
| `olist_orders_dataset.csv` | `raw.orders` |
| `olist_products_dataset.csv` | `raw.products` |
| `olist_sellers_dataset.csv` | `raw.sellers` |
| `product_category_name_translation.csv` | `raw.product_category_translation` |

`scripts/data_contract.py` — единственный источник истины для имён файлов, таблиц, порядка и списка колонок. Перед подключением с изменяющей данные транзакцией загрузчик проверяет каждый файл: существование, UTF-8 (допускается BOM), точный заголовок, одинаковое число полей во всех строках, SHA-256 и число строк.

Все исходные колонки в `raw` имеют тип `text`. Необрамлённые кавычками пустые поля PostgreSQL читает как `NULL`; опечатки `lenght` намеренно сохранены. В `raw` нет бизнес-ключей, ограничений и преобразований: это работа владельца модели `core`.

## 2. Загрузчик → SQL-слой

- Загрузка является полной заменой всех девяти таблиц, а не инкрементом.
- DDL, очистка, девять `COPY`, контроль числа строк и запись метаданных находятся в одной транзакции PostgreSQL.
- Advisory lock не допускает двух одновременных загрузок в одной базе.
- Ошибка откатывает транзакцию, включая уже выполненные `COPY`; процесс завершается ненулевым кодом.
- После успешного коммита `raw.load_state` содержит одну строку `success`, а `raw.load_manifest` — ровно девять строк с тем же `run_id`, хешами и количеством строк.
- Повторный запуск создаёт новый `run_id` и полностью заменяет данные только после успешной валидации.

После загрузки `scripts/run_sql.py` выполняет `model/**/*.sql`, затем `queries/**/*.sql`. Внутри каждого каталога порядок лексикографический по относительному пути; используйте числовые префиксы. Все SQL-файлы выполняются в отдельной общей транзакции с `search_path = core, raw, mart` и тайм-аутом 120 секунд (настраивается `SQL_STATEMENT_TIMEOUT_MS`).

Владелец SQL обязан обеспечить повторяемость своих скриптов (`CREATE ... IF NOT EXISTS`, `DROP ... IF EXISTS` или управляемую замену объектов). SQL должен строить модель только из `raw`, не менять исходные таблицы и не рассчитывать на ручные действия. Содержимое чужих файлов инфраструктурный слой не изменяет.

## 3. SQL/загрузчик → тесты

Интеграционные тесты запускаются только после нулевого кода выхода pipeline и проверяют:

1. единственное состояние `success` и девять записей manifest одного запуска;
2. совпадение `source_rows = loaded_rows` и фактических строк в каждой таблице;
3. точные имена и порядок колонок, тип `text` для всех исходных полей;
4. непустую `raw.geolocation`.

Бизнес-проверки результатов запросов добавляет владелец соответствующего SQL; инфраструктурные тесты не подменяют их.
